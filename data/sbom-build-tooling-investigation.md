# You Don't Know What You've Shipped — Maven build-tooling SBOM experiment

**Recorded:** 9 October 2026  
**Project:** `dev.noregressions:shipping-security-example:1.0.0-SNAPSHOT`  
**Scanner:** Trivy 0.74.0  
**Status:** Reproduced inventory and vulnerability scan; selected build-tool execution and XML-validation paths investigated; exploitability not established.

## Purpose

Demonstrate how vulnerability findings change when scanning an application-centric Maven SBOM versus an SBOM including resolved Maven build plugins and their transitive dependencies. The experiment holds the application and scanner constant, but changes the scope of the inventory supplied to the scanner.

## Inputs and commands

- Conventional CycloneDX JSON application SBOM: `target/bom.json` (generated by `org.cyclonedx:cyclonedx-maven-plugin:2.9.1:makeAggregateBom`). Its earlier generation log reported five components; Trivy's parsed package list includes the root project in addition to dependency artefacts.
- Expanded SBOM+ CycloneDX JSON: `target/sbom-plus-cyclonedx.json` (from SBOM+ Maven Plugin; previously observed 231 distinct component records).
- SBOM+ raw dependency report: 278 dependency records, comprising 13 application/test dependency records, 10 Maven plugin records, and 255 plugin-transitive occurrences. Repeated plugin-transitive occurrences can represent the same package version introduced by different plugins.

Commands, run from the Maven project's root directory:

```bash
mkdir -p target/security-results
trivy sbom --scanners vuln --format json --output target/security-results/application-trivy.json target/bom.json
trivy sbom --scanners vuln --format table --output target/security-results/application-trivy.txt target/bom.json
trivy sbom --scanners vuln --format json --output target/security-results/build-trivy.json target/sbom-plus-cyclonedx.json
trivy sbom --scanners vuln --format table --output target/security-results/build-trivy.txt target/sbom-plus-cyclonedx.json
```

Do not run `mvn clean` between producing and scanning SBOMs unless you intend to regenerate them.

## Observed results

| Measure | Application SBOM | Expanded SBOM+ inventory |
|---|---:|---:|
| Reported vulnerability matches | 18 | 77 |
| Critical | 0 | 2 |
| High | 8 | 38 |
| Medium | 10 | 32 |
| Low | 0 | 5 |

All 18 vulnerability/package/version matches from the application SBOM were also found in the expanded scan. The expanded scan reported **59 additional matches**, comparing the tuple `(VulnerabilityID, PkgName, InstalledVersion)`. This does **not** mean 59 different CVEs or 59 demonstrably exploitable vulnerabilities. Multiple versions of a single library can produce multiple matches for the same advisory.

### Application baseline

The 18 matches concern three Maven dependencies:

- `com.fasterxml.jackson.core:jackson-core:2.18.3` — 4 findings.
- `com.fasterxml.jackson.core:jackson-databind:2.18.3` — 13 findings.
- `org.apache.commons:commons-lang3:3.17.0` — 1 finding.

The Jackson results depend on specific parsing/deserialisation paths or configuration. A version-based match alone cannot determine whether those conditions occur in the application.

### Noteworthy build-tooling-related examples

| Component (resolved version) | Trivy advisory | Reported severity | Provenance or interpretative caution |
|---|---|---|---|
| `dom4j:dom4j:1.1` | CVE-2020-10683 | Critical | Maven Site Plugin's dependency graph; Site Plugin not shown executing in ordinary `mvn verify` log |

| `commons-io:commons-io:2.11.0` | CVE-2024-47554 | High | Appears in Maven Compiler Plugin's transitive dependency graph; compiler plugin executed and Commons IO JAR was included in its class realm; observed build did not load any `org.apache.commons.io` class |

| `org.eclipse.jetty:jetty-http:9.4.46.v20220331` | CVE-2026-2332 | High | Resolved through Maven Site Plugin; no evidence an HTTP server started during normal build |

**Commons Text caveat:** `org.apache.commons:commons-text:1.3` is in the expanded inventory (Site Plugin graph). The Trivy scan provided did **not** report CVE-2022-42889 against it. Do not claim the scanner detected Text4Shell in this example without a separate confirmed finding. That absence merits investigation into advisory coverage/matching.

## Interpretation and limitations

1. The experiment demonstrates **inventory-scope sensitivity of vulnerability reports**. It does not establish that a production artefact contains 77 vulnerabilities.
2. The 77 are vulnerability-to-component-version matches, not distinct CVEs, distinct risks, or exploits.
3. Maven `dependency:resolve-plugins -DincludeTransitive=true` describes plugins and their *resolved* dependencies; it is not an execution trace. An ordinary `mvn verify` build log previously showed Resources, Compiler, Surefire and JAR plugins executing. Other plugins may be invoked separately (e.g. CycloneDX), and some resolved plugins may never run in that build.
4. Component presence, executed plugin, reachable vulnerable code, attacker-controlled input, relevant privileges and practical exploitability are separate propositions.
5. In this run Trivy matched findings for components represented as `excluded` in the SBOM+ CycloneDX scope. That does not imply other SBOM consumers will handle that scope identically.
6. This inventory does not necessarily include the installed Maven distribution, the installed JDK, operating-system packages, or all external CI/CD tools; SBOM completeness is bounded by the collection method.
7. Trivy warned about third-party SBOM precision and unsupported hash algorithms. These warnings were not fatal; they are relevant to confidence in downstream interpretation.
8. Vulnerability databases and their match criteria change over time. Treat these as results captured on 9 October 2026, using Trivy 0.74.0, not timeless security verdicts.


## Follow-up investigation: actual execution and loading (9 October 2026)

### Compiler Plugin / Commons IO — CVE-2024-47554

In an instrumented `mvn -X clean compile` run, Maven reported that `maven-compiler-plugin:3.14.0` executed and populated its plugin class realm with `commons-io:2.11.0`. This is stronger evidence than merely resolving plugin dependencies: that JAR was **available to the executing plugin**. It is not proof any Commons IO method ran.

- The corrected `jdeps -verbose:class` check against the *compiler-plugin JAR itself* yielded no reported Commons IO class references (not a whole-transitive-graph result).
- JVM class-loading instrumentation using `JAVA_TOOL_OPTIONS="-Xlog:class+load=info:file=class-loading.log"` followed by `mvn clean compile` found no `org.apache.commons.io` classes loaded during the observed build.
- The build **did** load `org.codehaus.plexus.util.xml.XmlStreamReader` from the installed Maven runtime's `plexus-utils-3.6.1.jar`. This is **not** `org.apache.commons.io.input.XmlStreamReader` from Commons IO 2.11.0, which is the class relevant to the Commons IO advisory.

**Assessment:** dependency present in a populated plugin realm; plugin executed; no loading of the affected library observed in this particular compilation. No exploitability demonstrated. A different project or plugin execution path may behave differently. Only grepped outputs were provided for this case; keep the full compiler logs with the experiment if later available.

### CycloneDX Maven Plugin / CycloneDX Core Java — CVE-2025-64518

The separately instrumented SBOM-generation command was:

```bash
JAVA_TOOL_OPTIONS="-Xlog:class+load=info:file=cyclonedx-class-loading.log" \
  mvn -X org.cyclonedx:cyclonedx-maven-plugin:2.9.1:makeAggregateBom \
  > cyclonedx-debug.log 2>&1
```

The uploaded `cyclonedx-debug.log` confirms:

- `org.cyclonedx:cyclonedx-core-java:jar:9.0.5` was resolved **and included** in the `cyclonedx-maven-plugin:2.9.1` plugin class realm.
- `makeAggregateBom` executed successfully.
- The plugin reported `Writing and validating BOM (XML)` for `target/bom.xml`, followed by a corresponding JSON step, then `BUILD SUCCESS`.

The `cyclonedx-class-loading.log` records loading `org.cyclonedx.parsers.XmlParser` from `cyclonedx-core-java-9.0.5.jar`, as well as JDK `javax.xml.validation.SchemaFactory` and `javax.xml.validation.Validator`. This is direct evidence that XML-validation infrastructure was loaded during the operation, and the plugin's own log reports XML validation.

The previously inspected source path in `cyclonedx-maven-plugin:2.9.1` is: generate an XML BOM from an internal BOM model (`BomGeneratorFactory.createXml` / `toXmlString`), save it and validate the generated file via `bomParser.isValid(bomFile, schemaVersion())` with an `XmlParser`. The advisory describes unsafe XML schema validation in CycloneDX Core Java versions below 11.0.1, arising from incomplete XXE hardening. **Record the version-specific source/advisory links alongside the experiment before publication**; the uploaded debug and class-loading logs support execution but do not themselves establish the advisory's root cause.

**Assessment:** security/inventory tooling contains a version in the advisory's affected range; its XML parser and validation infrastructure were loaded, and the plugin reported validation in normal operation. The file validated here was generated by the plugin, not supplied as arbitrary untrusted XML. We have **not** demonstrated that attacker-controlled entities reach the vulnerable schema-validation code or that this Maven build is exploitable. The library's general-purpose XML validation API has a different trust boundary when used to process third-party SBOMs. Normal invocation is not an exploit demonstration.

### Three levels of evidence — same Maven project

| Case | Dependency available | Plugin executed | Relevant code activity observed | Untrusted input / exploitation |
|---|---|---|---|---|
| Maven Site Plugin / `dom4j:1.1` or Maven-core 3.2.5 | Resolved | Not observed in `mvn verify` | No | Not established |
| Maven Compiler Plugin / `commons-io:2.11.0` | Populated in plugin class realm | Yes | No Commons IO classes loaded in tested compilation | Not established |
| CycloneDX Maven Plugin / `cyclonedx-core-java:9.0.5` | Populated in plugin class realm | Yes, during SBOM generation | XML parser and JDK validation classes loaded; XML validation reported | Not established |

**Key takeaway:** the inventory tool that generated the original, application-focused SBOM itself uses a library with a reported vulnerability. This concerns the **build/security-assessment environment**, not a claim that the vulnerable library is packaged in the application's JAR. The point is the need to examine the trust placed in tooling that builds *and assesses* software.

### Follow-up, if required

Investigate the precise `XmlParser.isValid` implementation in 9.0.5 against the patch for CVE-2025-64518; identify whether an attacker can cause untrusted XML to be validated in any relevant workflow; compare secure processing and external DTD/schema restrictions. Re-test with a fixed, supported version of the security tooling where practical. Do not use the raw CVE count as risk ranking.

## Suggested narrative for the article/talk

A small Maven application passed its tests. The conventional CycloneDX application SBOM led Trivy to report 18 vulnerability matches. Without changing the application or scanner, a broader SBOM including build-plugin dependency graphs led the same scanner to report 77 matches, including two critical. The result does not mean the application suddenly became more vulnerable; it means the scan was asked a different question. Follow-up checks distinguish resolved Site Plugin dependencies from Commons IO present but not observed loading during compilation, and from CycloneDX Core Java XML validation actually used by the security tool that generated the SBOM. The latter is a vulnerability finding in the tooling used to assess the application, not evidence that the application ships the affected library or that the validation operation is exploitable.

## Next investigation: three representative cases

1. **Compiler Plugin → Commons IO 2.11.0 → CVE-2024-47554.** Inspect the executed plugin path; check whether Commons IO's `XmlStreamReader` is invoked with untrusted XML. Even an executed plugin is not necessarily vulnerable in the exercised path.
2. **CycloneDX Plugin → cyclonedx-core-java 9.0.5 → CVE-2025-64518.** Confirm the plugin ran during SBOM generation; examine whether attacker-controlled XML reaches the affected BOM validation code path. Note that JSON SBOM generation by itself may not exercise vulnerable XML parsing.
3. **Site Plugin → dom4j 1.1 → CVE-2020-10683.** Verify the Site Plugin is only resolved, not executed in `mvn verify`; if a separate `mvn site` is tested, examine its actual XML parsing behaviour in isolation.

Capture the exact Maven/plugin versions, command lines and logs for each test. No exploit claim should be made based solely on the advisory and dependency graph.
